# **StudentHub: Comprehensive Platform Architecture and Ecosystem Research Report**

## **Area 1: Campus Wallet Feature Map**

The foundational architecture of the StudentHub ecosystem is predicated entirely upon the abstraction of "platform credits." To remain legally viable within the Philippine regulatory environment, the platform must meticulously adhere to the definitions set forth by the Bangko Sentral ng Pilipinas (BSP). Under BSP Circular No. 1166, which amends the regulations governing Electronic Money Issuers (EMIs), a critical exemption is provided for closed-loop electronic wallet systems.1 The regulatory framework explicitly defines a closed-loop electronic wallet as an arrangement wherein the stored value is accepted as a means of payment solely by the merchant-issuer, with the merchant-issuer and its subsidiaries or affiliates considered as a single entity.2 Because StudentHub operates within a single institutional ecosystem and restricts the redemption of its platform credits exclusively to local intranet services and internet access provisions, it securely occupies this closed-loop carve-out. This classification legally shields the student organization from the stringent capitalization, liquidity, and trust account requirements imposed on open-loop EMIs.3 Consequently, all technical design decisions within the ledger system must strictly enforce the non-cashable and non-transferable nature of these platform credits.

The platform's credit operations demand a robust, transactional accounting ledger capable of processing high-frequency, low-latency events across various ingestion and deduction mechanisms. The physical loading of credits via coin insertion operates through an asynchronous event chain. When a student deposits a coin, the ESP32 hardware publishes an event to the local Mosquitto MQTT broker. The Node.js real-time engine subscribes to this topic, validates the hardware signature, and executes an atomic database transaction in PostgreSQL to increment the user's platform credit balance. Conversely, the digital loading of credits relies on payment gateway integrations, specifically Xendit for GCash and PayMaya transactions. The architecture must implement an idempotent webhook receiver to process Xendit's payment confirmations. Idempotency is critical here; the system must gracefully handle duplicate webhook deliveries caused by network retries without inadvertently double-crediting the student's account. Furthermore, the system must accommodate administrative and organizational grants. Administrators require an interface to inject credits directly into user accounts to facilitate event-driven promotions, reward distributions, or compensation for infrastructure downtime. Similarly, student organizations necessitate the ability to issue bulk credit grants to specific cohorts, such as crediting the accounts of event volunteers.

The deduction of credits—the debit operations—forms the primary economic utility of the platform. The most common transaction involves the purchase of a WiFi session. When a user initiates a session, the business logic deducts the corresponding platform credits from their ledger and interfaces with the OpenNDS captive portal daemon. Specifically, the system utilizes the ndsctl auth IP|MAC command mechanism to instruct OpenNDS to grant network routing privileges to the device for a calculated temporal duration.5 Beyond internet access, the platform API allows approved intranet services to execute debits. When a student utilizes an approved third-party application, the application calls the local platform API, which deducts the required credits and returns a cryptographic confirmation of the transaction.

Session management mechanics introduce complex edge cases, particularly regarding the pausing and refunding of active WiFi time. Commercial vending systems offer users the ability to pause their internet access to preserve unutilized time. Implementing this within the OpenNDS framework requires a carefully choreographed sequence. When a student requests a pause, the backend must execute the /usr/bin/ndsctl deauth IP|MAC command.5 This action forces the OpenNDS daemon to terminate the routing grant and triggers the configured BinAuth script.6 The OpenNDS daemon passes highly specific arguments to the BinAuth script during a deauthentication event, including the session\_start and session\_end timestamps.6 The Node.js bridge intercepts these arguments, calculates the precise duration consumed, determines the residual unused time, converts this temporal value back into the equivalent platform credits, and credits the user's ledger via a transactional refund.

Administrative refunds for failed sessions operate on a similar ledger principle but require strict auditing. When a network anomaly disrupts a session, administrators can execute a manual refund. This operation restores the platform credits to the user while generating an immutable audit log entry detailing the administrator's identity and the mandated reason for the intervention.

The implementation of credit expiry policies presents a unique intersection of technical design and economic strategy within a school's income-generating project context. While commercial telecommunications load in the Philippines is subject to standardized one-year expiry regulations, a closed-loop campus ecosystem benefits from aligning expiration policies with the academic calendar. Expiring unused credits at the culmination of the academic year or semester prevents the indefinite accumulation of digital liabilities on the student organization's balance sheet. However, the system must clearly communicate these expiration policies within the captive portal interface to maintain transparency.

The concept of peer-to-peer credit transfers introduces severe legal vulnerabilities. Permitting students to transfer raw platform credits to one another risks transforming the localized credits into a generalized medium of exchange. If students begin utilizing platform credits to settle external personal debts or pay for goods outside the platform's purview, the system arguably breaches the boundaries of a closed-loop system, thereby risking reclassification as an unauthorized open-loop electronic wallet subject to BSP sanctions.4 To mitigate this risk, raw credit transfers must be technically prohibited. Instead, the architecture should support a controlled alternative mechanism, such as "Session Gifting." In this model, a student debits their own credit balance to authorize an ndsctl auth grant directly for a peer's device, ensuring the economic value is instantly consumed as a platform service rather than circulated as currency.

Transitioning to the credit account identity model, the platform must balance immediate accessibility with persistent tracking. Modern mobile operating systems, including iOS and Android, deploy aggressive MAC address randomization to prevent cross-network tracking. Consequently, relying on the hardware MAC address as the primary database key for user identity—a standard practice in legacy commercial WiFi vendos—results in orphaned balances and fragmented user histories. To circumvent this, StudentHub employs a browser token-based identity architecture. Upon initial connection to the captive portal, the backend provisions a cryptographically secure, HTTP-only cookie to the user's device. This ephemeral, anonymous credit account allows a student to drop coins and purchase internet access without enduring a tedious registration process.

However, because browser cookies are susceptible to accidental deletion, the platform must provide a seamless upgrade path to a named credit account. A named account links the ephemeral browser token to a verified institutional identity, enabling multi-device synchronization and balance recovery. Following the principle of data minimization suitable for a campus environment, the required data schema for a named account should be restricted to the Student ID number, the student's academic program and year, and a hashed Personal Identification Number (PIN).

Account recovery in an intranet-first environment presents distinct operational challenges. Given that local campus networks often lack reliable outbound SMTP email servers for traditional password reset workflows, alternative recovery vectors must be established. The architecture provides several mechanisms for this. The primary fallback is a physical administrative reset managed via the dashboard at the student council office. Alternatively, the platform can utilize a localized SMS gateway. By deploying an open-source application like Textbee on an inexpensive Android device connected to the internal network, the Laravel backend can execute local REST API calls to dispatch SMS One-Time Passwords (OTPs) for account recovery.8 This eliminates the recurring operational expenditures associated with commercial cloud SMS providers while maintaining robust recovery capabilities.

To achieve functional supremacy over standard commercial vending software, the WiFi session feature set must exhibit complete behavioral parity. The pause and resume mechanics must operate seamlessly; pausing stops the timer and blocks external internet access, while resuming re-authenticates the device via ndsctl auth utilizing the mathematically preserved remaining seconds.9 The token-based identity model inherently facilitates session transferability. A student can initiate a session on a mobile device, log into the named account via the captive portal on a laptop, and seamlessly migrate the active temporal grant to the new hardware. Furthermore, the OpenNDS daemon inherently supports auto-resume capabilities; if a device enters a sleep state and disconnects, reconnecting within the active temporal window immediately restores routing privileges without requiring a secondary payment interaction.

Administrative wallet controls constitute the final pillar of the credit system. The centralized dashboard, interfacing directly with the PostgreSQL data store, provides organizational leaders with comprehensive oversight. Administrators possess the capability to execute ad-hoc free session grants targeting specific devices or student accounts, heavily utilizing the ndsctl auth command to bypass credit deductions.5 Bulk grants can be orchestrated to target specific academic groups, utilizing database tagging to distribute credits to an entire class roster simultaneously. For institutional requirements, such as a mandated free access window from 7:00 AM to 8:00 AM, the system employs cron-scheduled scripts to temporarily manipulate the OpenNDS walled garden, allowing unrestricted routing before automatically reverting to the credit-gated state. Finally, the administrative suite must include strict access control mechanisms to revoke or suspend accounts demonstrating abusive network behavior or engaging in payment disputes, ensuring the integrity of the campus network.

## **Area 2: Platform API Design**

The Platform API represents the architectural differentiator that elevates StudentHub from a sophisticated internet gateway to an extensible campus ecosystem. This application programming interface provides the localized infrastructure necessary for student developers to build, deploy, and monetize intranet applications without circumventing the core economic model. The paramount design constraint of this API is its strict isolation; it operates exclusively within the local network boundary, rendering it inaccessible from the public internet. This isolation mitigates external attack vectors and guarantees that all financial abstractions remain contained within the physical campus.

### **API Surface and Endpoint Mapping**

The RESTful API surface must accommodate the full lifecycle of credit and session management for third-party consumers. The architecture defines a structured mapping of endpoints, methods, and cryptographic boundaries.

| Endpoint | Method | Purpose | Inputs | Outputs | Rate Limit Consideration |

| /api/v1/wallet/balance | GET | Retrieve a student's current available platform credit balance based on their token. | device\_token | balance (float) | High (e.g., 60 req/min) to allow rapid UI polling. |
| /api/v1/wallet/debit | POST | Deduct credits from a student's wallet in exchange for an application-specific service. | amount, purpose\_tag, device\_token | transaction\_id, status | Strict (e.g., 10 req/min) to prevent rapid depletion attacks. |
| /api/v1/wallet/credit | POST | Inject credits into a student's wallet, typically as a reward for completing a specific action within the app. | amount, purpose\_tag, device\_token | transaction\_id, status | Strict, coupled with daily absolute maximums per API key. |

### **API Authentication and Governance Flow**

The governance of the platform API is central to maintaining the ecosystem's security posture. Every application hosted within the Proxmox environment must be explicitly authorized by the central administration. The authentication model relies on scoped, cryptographically secure API keys generated by the Laravel backend. When an application is approved, it is issued a primary key accompanied by a specific permissions bitmap. This scope determines whether the application holds read-only access (permitting balance checks but no debits), debit-only access, or bidirectional credit/debit capabilities.

Network-level enforcement guarantees that these API keys cannot be utilized maliciously by unauthorized actors. The OpenWrt gateway implements strict iptables rules ensuring that the API endpoint subnet drops any incoming packets originating from the Wide Area Network (WAN) interface. Furthermore, the Laravel application layer implements an IP allowlist mechanism, strictly rejecting API requests that do not originate from the designated Docker subnet housing the Coolify applications. To address key compromise, the system architecture requires a zero-downtime key rotation mechanism. Administrators can generate a secondary, overlapping API key for an application, allowing the developer to update their environment variables within the Coolify dashboard and restart their container before the primary key is permanently revoked.

The application registration and deployment flow operates as a structured pipeline. A student developer submits a comprehensive proposal detailing the application's nomenclature, its intended campus utility, the required API permission scopes, and the Git repository URL containing the source code. Upon administrative review and approval via the StudentHub dashboard, the system provisions the requested API keys and utilizes Coolify's automated deployment pipelines to pull, build, and run the Dockerized application.10 Crucially, the administrator then modifies the OpenNDS walled garden Access Control List (ACL) to include the application's internal local IP address. This specific configuration ensures that unauthenticated student devices connected to the campus WiFi can seamlessly route to the new application prior to purchasing internet access.

### **Payment Abstraction and Ecosystem Legalities**

The defining regulatory constraint of the StudentHub platform is the absolute prohibition of direct real-money transactions by third-party applications. To maintain the BSP Circular 1166 closed-loop exemption, the platform must serve as the sole financial intermediary.2 Hosted applications are strictly forbidden from embedding their own independent payment gateways, displaying personal GCash QR codes, or soliciting raw cash. All monetary inflow must route through the central StudentHub credit top-up system, with applications acting solely as consumers of the abstracted platform credits.

Enforcing this constraint requires robust technical and contractual mechanisms. Technically, the Proxmox gateway must implement egress firewall rules on the internal subnet hosting the Coolify containers. These rules explicitly drop outbound packets directed toward known payment processor IP ranges or domain names (e.g., Xendit, PayMongo, Stripe), physically preventing an application from initiating an external financial transaction. Contractually, the application developer terms of service must explicitly outline this restriction. The legal agreement must state that all transactions must be executed via platform credits, mandate local-only deployments, strictly prohibit the exfiltration of student data to external servers, and establish that the central student organization bears no liability for app-specific functional disputes. Any violation of these terms triggers an immediate, automated suspension of the application's API key and the halting of its respective Docker container.

### **Use Case Validation**

Validating the API design against anticipated student applications ensures the architecture's practical viability while highlighting specific edge cases.

The deployment of a "School Ipon" or digital savings application requires careful legal navigation. In the Philippine regulatory context, accepting funds from the public for the purpose of safekeeping and subsequent withdrawal constitutes deposit-taking, an activity strictly reserved for licensed banking institutions.3 If a student application allows users to deposit coins and later withdraw that exact monetary value in cash, the platform violates banking laws. Therefore, the safest and only viable structure is to mandate that the "ipon" balance remains a non-cashable sub-ledger of platform credits. A student depositing physical coins into a slot designated for savings triggers a wallet/credit API call tagged with a specific purpose=ipon identifier. These specialized credits cannot be liquidated but can be accumulated and exclusively redeemed for high-value platform services, such as a bulk semester-long WiFi pass or premium merchandise at the school store. The data model requires the central wallet to support tagged sub-balances to segregate these restricted funds from standard consumable credits.

A donation application serves as a prime example of compliant closed-loop circulation. A student interacting with the app selects a charitable cause and authorizes a donation of 5 credits. The application executes a POST request to /api/v1/wallet/debit. The platform backend verifies the user's token and executes the debit. If the student possesses an insufficient balance, the API immediately returns an HTTP 402 Payment Required status code, prompting the application to render a graceful error message suggesting a platform top-up. Upon a successful debit, the credits are not destroyed; rather, they are algorithmically transferred to an administrative "Org Master Account." This organizational account pools the donated digital resources, which the student council can subsequently utilize to grant free WiFi access to organizational volunteers or subsidize the operational costs of the platform itself.

Event ticketing applications validate the necessity of the verification endpoint. When a student organization sells access to an event via a Coolify-hosted application, the student executes a payment via a wallet debit. The application then generates a cryptographically signed QR ticket. At the event perimeter, door personnel scan the QR code, triggering a call to the /api/v1/transaction/verify endpoint. The platform confirms the authenticity of the transaction hash and ensures the ticket has not been previously utilized, mitigating fraud without requiring the ticketing app to maintain a complex, highly secure internal database.

Finally, e-voting applications demonstrate the utility of the identity layer without invoking the financial ledger. A voting platform requires absolute assurance that the user interacting with the system is a currently enrolled, eligible student. By calling the /api/v1/student/profile endpoint using the browser token, the voting application can confirm the student's active status and retrieve their academic program to serve the appropriate localized ballot. The API must strictly enforce privacy constraints here, ensuring the endpoint returns only the minimum necessary boolean validation and broad demographic data, specifically excluding sensitive information such as exact academic grades or physical addresses.

## **Area 3: Proxmox Architecture**

The underlying infrastructure mandates the use of Proxmox Virtual Environment (VE) operating on x86 hardware architecture. Proxmox provides the essential hypervisor capabilities to segment the complex networking requirements of the captive portal from the aggressive routing behaviors of modern container orchestration tools. A recognized architectural conflict exists between the iptables rules generated by OpenNDS and the dynamic networking modifications executed by Traefik, the reverse proxy utilized by Coolify. To neutralize this risk, the architecture dictates strict isolation: routing and captive portal operations reside in a dedicated Virtual Machine, while application hosting occurs in a distinct, separate environment.

### **VM and LXC Topology**

The deployment strategy is optimized for a budget-tier hardware profile, specifically targeting devices such as the Intel N100 Mini PC equipped with 16GB of DDR5 RAM and NVMe storage. Table 2 delineates the precise container and virtual machine distribution required to maximize performance while ensuring operational stability.

| Container / VM | Type | Operating System | Primary Purpose | RAM Allocation |
| :---- | :---- | :---- | :---- | :---- |
| **Gateway** | VM 1 | OpenWrt x86 | Primary routing, DHCP server, firewall, VLAN termination, and OpenNDS captive portal execution. | 1024 MB |
| **App Server** | VM 2 | Ubuntu 22.04 LTS | Docker host, Coolify orchestration, Traefik reverse proxy, and all third-party student applications. | 8192 MB |
| **Database** | LXC 1 | Debian 12 | Persistent data storage via PostgreSQL 16, connection pooling via PgBouncer, and fast session caching via Redis. | 2048 MB |
| **Real-time Engine** | LXC 2 | Debian 12 | Node.js asynchronous event processing, Laravel queue workers, and the MQTT-to-HTTP API bridge. | 1024 MB |
| **MQTT Broker** | LXC 3 | Alpine Linux | Mosquitto MQTT message broker to receive low-latency hardware interrupts from the ESP32 coin slots. | 256 MB |
| **Monitoring** | LXC 4 | Debian 12 | Metrics aggregation via Prometheus and dashboard visualization via Grafana. | 512 MB |
| **Hypervisor** | Host | Proxmox VE 8.x | Base system overhead, storage management (ZFS/LVM), and network bridging. | \~3000 MB |

The decision to deploy OpenWrt x86 as the gateway operating system in VM1 rather than a heavier alternative like OPNsense or pfSense is driven by hardware constraints. OpenWrt requires a significantly smaller memory footprint and lower CPU overhead for basic Network Address Translation (NAT) and routing tasks. Crucially, OpenWrt maintains native, highly mature package support for OpenNDS, simplifying the captive portal implementation. OpenNDS must run strictly inside VM1; deploying it as a separate LXC that VM1 routes traffic through introduces unnecessary network hops, complicates NAT reflection rules, and increases the latency of the initial captive portal redirection.

### **NIC Passthrough and VLAN Design**

The physical network interface configuration is highly dependent on the hardware constraints of the mini PC. While deploying a mini PC with dual physical Network Interface Cards (NICs) is optimal, the Proxmox networking stack can seamlessly accommodate a single-NIC configuration via 802.1Q VLAN tagging.

The architecture utilizes Proxmox virtual bridges (vmbr) to abstract the physical hardware.

* **vmbr0 (WAN Bridge):** This virtual bridge is connected to the physical port receiving the upstream ISP connection. VM1 attaches a virtual network interface to vmbr0 to acquire the external public or Carrier-Grade NAT IP address.  
* **vmbr1 (LAN/Trunk Bridge):** This virtual bridge serves as the internal backbone. It connects to the physical port linking the Proxmox host to an external managed switch and the subsequent UniFi or TP-Link Omada access points.

Within VM1 (OpenWrt), complex VLAN configurations are instantiated on the virtual interface connected to vmbr1. OpenWrt acts as the router on a stick, handling inter-VLAN routing and DHCP assignments.

* **VLAN 10 (Student WiFi):** The primary, unsecured wireless broadcast. All traffic originating on this subnet is aggressively intercepted by OpenNDS and forced through the captive portal authentication flow.  
* **VLAN 20 (Admin/Staff):** A secured, encrypted broadcast dedicated to faculty and system administrators. Traffic on this subnet explicitly bypasses the OpenNDS daemon, granting unrestricted outbound internet routing.  
* **VLAN 30 (Intranet Apps):** The highly secure internal server subnet. VM2 and all LXC containers reside on this VLAN. To ensure functionality, OpenWrt maintains strict walled-garden routing rules that permit unauthenticated devices on VLAN 10 to access specific IP addresses on VLAN 30, thereby allowing students to interact with the portal and third-party apps before purchasing internet access.  
* **VLAN 99 (Proxmox Management):** A completely isolated subnet dedicated to accessing the Proxmox web GUI and SSH interfaces. This network must never be accessible from the student-facing access points.

### **Automation and Fast Deployment**

To satisfy the requirement for rapid development and iterative deployment, the infrastructure heavily leverages community automation and native Proxmox provisioning features. The widely utilized Proxmox Helper Scripts repository (community-scripts.github.io) provides invaluable, pre-configured bash commands for generating optimized LXC environments.10 Verified, production-ready scripts are available for deploying PostgreSQL, Redis, and Mosquitto directly into lightweight Alpine or Debian containers.10 Furthermore, a dedicated add-on script exists to automate the complex installation of Coolify over an existing Debian or Ubuntu instance.11 The correct methodology for utilizing these community scripts involves reviewing the source code repository for security validation, optionally pinning the execution to a specific Git commit hash to ensure immutability, and executing the scripts via the Proxmox host shell in "Advanced Mode" to manually dictate the target VLANs and static IP allocations.

For the deployment of VM2 (the App Server), the architecture utilizes Proxmox's native cloud-init functionality. Rather than executing manual ISO installations, the administrator prepares a customized Ubuntu Server template embedded with a cloud-init drive. During the cloning process, the Proxmox API automatically injects authorized SSH keys, configures the system hostname, dynamically expands the logical volume to match the requested disk size, and applies the static IP configuration for VLAN 30\. This methodology reduces the provisioning time of the application server from thirty minutes to mere seconds. By combining the Proxmox Helper Scripts for the LXC database tiers and cloud-init for the application VMs, a developer can transition a bare-metal Proxmox installation into a fully operational StudentHub staging environment in under two hours.

### **Backup and Disaster Recovery**

Data persistence and rapid disaster recovery are critical for maintaining the integrity of the economic ledger. Proxmox's integrated vzdump utility provides the mechanism for capturing point-in-time snapshots of the virtual environments.

The backup schedule requires daily execution during off-peak hours (e.g., 3:00 AM) to minimize disk I/O contention. The Database LXC, which houses the critical PostgreSQL credit ledger, necessitates a highly consistent snapshot mode backup. Conversely, the App Server (VM2) can be backed up using a standard suspend mode if Docker container states do not demand absolute millisecond continuity.

Regarding storage targets, backups must never reside on the primary NVMe drive housing the active virtual machines. For budget deployments, connecting an external USB 3.0 or Type-C hard disk drive directly to the Proxmox host provides a cost-effective local repository. As the platform scales, deploying an independent, low-power machine operating Proxmox Backup Server (PBS) facilitates network-based, incremental, and heavily deduplicated backups.10

The disaster recovery objectives are optimized for minimal downtime. If VM1 (the gateway) experiences catastrophic software corruption resulting from a failed OpenWrt package upgrade, the system administrator can initiate a full restoration from the latest local snapshot. Given the minuscule disk footprint of the OpenWrt operating system, a qmrestore command typically completes, and the system reboots into a functional state within five to ten minutes. On the N100 hardware tier, maintaining a live, synchronized warm standby node is technically unfeasible without a clustered storage architecture, making rapid snapshot restoration the primary defense mechanism against failure.

## **Area 4: Public Domain and External Access Strategy**

The StudentHub platform is fundamentally designed as an isolated, school-first intranet solution. However, specific administrative functions and public-facing informational applications eventually require controlled exposure to the broader internet. Designing the domain, SSL, and ingress architecture from the outset prevents future security compromises.

### **Domain and SSL Certificate Strategy**

The selection of the domain name space dictates both the legal requirements and the annual operational expenditures. While acquiring a .edu.ph domain theoretically provides the highest institutional credibility, it requires formal, bureaucratic accreditation from the Department of Education (DepEd) or the Commission on Higher Education (CHED).16 For a localized student organization project, overcoming this administrative barrier is often impractical. Therefore, registering a standard .ph or .com.ph domain is the optimal strategic choice. Market research indicates that the standard annual registration fee for a .ph or .com.ph domain currently ranges between $46.00 and $62.00 USD, depending on the chosen registrar.17

To ensure seamless navigation between the internal campus and the external internet, the platform must implement a split-horizon DNS architecture. Internally, the OpenWrt gateway's dnsmasq service intercepts requests for the primary domain (e.g., portal.studenthub.ph) and resolves them directly to the local private IP address on VLAN 30 (e.g., 192.168.30.50). Externally, authoritative DNS records hosted on Cloudflare point to the designated public ingress vectors.

Securing the internal network with valid Transport Layer Security (HTTPS) certificates presents a unique challenge, as standard HTTP-01 Let's Encrypt validation fails when the server resides behind a NAT on a private RFC 1918 IP address. The architecture resolves this by employing the DNS-01 ACME challenge methodology. The Traefik reverse proxy, managed natively by Coolify within VM2, is configured to communicate with the Cloudflare API. When a certificate is required, Traefik requests a wildcard certificate (\*.studenthub.ph) and proves domain ownership by dynamically injecting a temporary TXT record into the Cloudflare DNS zone. Let's Encrypt verifies the TXT record and issues the trusted certificate directly to the internal server. This automated process secures all internal subdomains—ranging from the payment portal to library systems—without ever requiring the Proxmox firewall to expose port 80 to the public internet.

### **External Access Options**

When the organization determines it is appropriate to expose specific applications to the public, directly port-forwarding the internal network through the ISP router introduces unacceptable security vulnerabilities.

The preferred methodology for selective public exposure is the utilization of a Cloudflare Tunnel (cloudflared). This architecture involves deploying a lightweight Docker container within the VM2 environment. The cloudflared daemon establishes an outbound, encrypted connection to the Cloudflare edge network. External users connect to the Cloudflare proxy, which routes the traffic through the established tunnel directly to the internal Coolify applications. This mechanism requires zero inbound open ports on the Proxmox firewall and entirely eliminates the necessity for a static public IP address from the campus ISP. It is the optimal choice for exposing public-facing apps, such as school announcements or organizational election results.

Conversely, for highly sensitive administrative access, the platform relies on VPN-gated ingress. Administrators must install a WireGuard VPN profile on their personal devices to establish a secure, encrypted tunnel into VLAN 20 or VLAN 99\. This approach is absolutely mandatory for protecting the Proxmox management GUI, the Laravel backend administrative panels, and direct SSH access to the database containers.

Certain critical components of the architecture must be designated as strictly private and never exposed to the public internet under any configuration. These include the StudentHub Platform API, the Mosquitto MQTT broker handling hardware interrupts, and the Node.js ndsctl bridging engine. Exposing the API or the MQTT broker externally introduces severe vulnerabilities, potentially allowing malicious actors to manipulate the economic ledger or spoof hardware coin-drop events from outside the campus.

## **Area 5: Scaling Plan**

The platform's initial deployment on highly efficient, consumer-grade mini PCs (such as the Intel N100) provides an exceptional balance of cost and performance. However, this hardware class possesses distinct physiological limits that necessitate a predefined scaling trajectory as the platform's user base expands.

### **The Mini PC Ceiling**

Contrary to expectations, the primary bottleneck for an Intel N100 operating as a captive portal gateway is not raw CPU cycle availability or RAM exhaustion, but rather the limitations of the Linux kernel's network connection tracking table (nf\_conntrack). When acting as a router, the Linux kernel must track the state of every active TCP and UDP flow to perform Network Address Translation (NAT) and firewall filtering.19

As the volume of concurrent users escalates toward 500 active devices, the sheer quantity of parallel connections can rapidly deplete the available entries in the conntrack table. Research indicates that modern web browsing, characterized by devices simultaneously opening dozens of short-lived connections to various content delivery networks, can generate thousands of connections per second.19 If a sudden influx of students saturates the network, the connection rate can easily overwhelm the default table limits, leading to instantaneous packet drops, localized denial-of-service conditions, and severe perceived latency.19

System administrators must vigilantly monitor early warning metrics to preempt failure. These metrics include tracking the absolute conntrack table usage (sysctl net.netfilter.nf\_conntrack\_count), monitoring CPU interrupt request (IRQ) rates caused by excessive packet processing, and observing elevated latency in PostgreSQL query execution. Assuming a consistent load of 200 to 500 active daily users interacting with 10 to 15 lightweight Docker containers, an appropriately tuned 16GB mini PC can realistically sustain operations for one to two academic years before requiring architectural expansion.

### **Scaling the Wallet and Session Layer**

As the platform scales toward 1,000 concurrent sessions, the database architecture requires immediate augmentation. PostgreSQL operates on a process-per-connection model, meaning thousands of direct client connections will rapidly exhaust memory resources and degrade query performance. To mitigate this, introducing a connection pooler, specifically PgBouncer, is mandatory. PgBouncer multiplexes thousands of incoming client requests into a small, highly efficient pool of persistent PostgreSQL connections. This component should be deployed within the Database LXC during Phase 1 to ensure architectural resilience from the outset.

Similarly, the Redis deployment utilized for session caching and API rate limiting must be configured to accommodate increased scale. At higher data volumes, relying solely on in-memory storage introduces the risk of catastrophic session loss during an unexpected power event. Redis must be configured for persistence, utilizing an Append-Only File (AOF) configuration synchronized every second, ensuring that active session states and temporary API tokens can be recovered immediately upon system reboot. The Mosquitto MQTT broker, conversely, is highly efficient; empirical data demonstrates that Mosquitto can handle tens of thousands of messages per second on modest hardware, ensuring it will not become a bottleneck for processing coin-drop events at any realistic campus scale.

### **Migration Path to Rack Servers**

When the network sustains continuous loads exceeding 1,000 concurrent users or demands the deployment of highly complex, resource-intensive third-party applications, a migration to enterprise-grade server hardware becomes imperative.

The Philippine surplus and refurbished hardware market provides accessible avenues for this expansion. Used enterprise rack servers, such as the Dell PowerEdge R630 or R730 equipped with dual Intel Xeon E5 v3/v4 processors, are readily available and typically priced between PHP 15,000 and PHP 35,000, depending on the memory configuration and disk arrays. These platforms provide the crucial PCIe lanes necessary to support 10-Gigabit Enterprise NICs and robust, highly available hardware RAID configurations.

Because the entire StudentHub infrastructure is virtualized within the Proxmox hypervisor, the migration process is exceptionally streamlined, operating at the virtual machine level rather than requiring complex OS-level rebuilds. The administrator executes a full vzdump backup of VM1, VM2, and the required LXC containers. These archive files are transferred to the newly provisioned Dell server, where a qmrestore and pct restore command rebuilds the precise environment. The system downtime is strictly limited to the duration of the archive file transfer and restoration processes.

### **Proxmox Clustering**

If budget constraints prevent the acquisition of enterprise rack servers, horizontal scaling via a Proxmox cluster utilizing multiple mini PCs provides an alternative pathway.

However, Proxmox clustering possesses strict quorum requirements to prevent split-brain synchronization errors during network partitions. A viable cluster demands a minimum of three voting nodes. If the organization purchases a second mini PC, they must deploy a lightweight "QDevice" (Quorum Device) on a separate, inexpensive piece of hardware, such as a Raspberry Pi or an external cloud Virtual Private Server (VPS), to provide the necessary third tie-breaking vote.

While clustering enables centralized management and the potential for High Availability (HA) failover, implementing distributed shared storage systems like Ceph on consumer-grade mini PCs is highly problematic. Ceph requires enterprise-grade SSDs and dedicated 10Gbps networking backbones to perform synchronously without severe input/output latency degradation. Therefore, a clustered mini PC architecture should rely on ZFS asynchronous replication between local storage drives rather than true distributed shared storage, accepting minor data latency in exchange for architectural stability.

### **Technical Gap Research and Feature Resolution**

The audit reveals specific technical features that require distinct implementation strategies to maintain parity without overwhelming the hardware.

Commercial vending platforms frequently deploy **Anti-VPN enforcement** mechanisms to prevent students from sharing a single authenticated session across multiple devices via a VPN tunnel. On Linux-based gateways, implementing robust Anti-VPN protocols necessitates Deep Packet Inspection (DPI) or aggressive port-blocking algorithms. Given the limited processing capacity of the N100 hardware, performing DPI on hundreds of concurrent connections will drastically reduce overall network throughput. Furthermore, maintaining static blacklists of known VPN provider IP addresses is an endless, ineffective administrative burden. Because StudentHub utilizes a token-based identity model, the system inherently restricts a single token to a single active device, severely mitigating the efficacy of session sharing and rendering complex Anti-VPN enforcement unnecessary for this context.

**Bandwidth throttling** is a fundamental requirement to prevent a single user from consuming the entire ISP allocation. Rather than forcing the developer to construct highly complex Linux traffic control (tc) queues, OpenNDS provides native, highly efficient throttling capabilities. When the backend initiates a session, it can directly pass the uploadrate and downloadrate arguments to the ndsctl auth command.9 OpenNDS automatically manages the underlying packet shaping, seamlessly applying the limitations without requiring secondary intervention.

The generation of **Voucher codes** serves as a vital alternative payment and promotion method. The complexity of adding this feature is minimal. The Laravel backend requires a module to generate cryptographically secure, alphanumeric strings, associating them with a defined volume of platform credits in the PostgreSQL database. When a student enters a valid code into the captive portal UI, the system executes a wallet/credit operation, securely invalidating the voucher payload upon success.

Finally, integrating **SMS notifications** for low-balance warnings or security alerts significantly enhances the user experience. However, subscribing to commercial cloud SMS providers introduces prohibitive recurring costs for a student organization. The solution leverages Textbee, a self-hosted SMS gateway that utilizes an inexpensive, physical Android phone connected to the campus network.21 The Laravel application dispatches standard HTTP POST requests to the local Textbee API endpoint (/api/v1/gateway/devices/{ID}/send-sms), passing the target student's phone number and the message payload.8 The Android device physically transmits the SMS using standard local carrier rates, entirely eliminating cloud API fees and keeping notification data localized.

## **Area 7: Developer Experience and Fast Deployment**

Optimizing the developer experience is paramount to ensuring the rapid iteration and long-term maintainability of the StudentHub platform.

The extensive utilization of **Proxmox Helper Scripts** from the community repository (community-scripts.github.io) dramatically accelerates the configuration of the foundational database and message broker tiers.10 Verified, production-grade deployment scripts exist for PostgreSQL, Redis, Mosquitto, and Node.js.10 Furthermore, the repository provides an add-on script to streamline the complex deployment of the Coolify orchestration engine over a standard Debian or Ubuntu container.11 To utilize these scripts safely, the system administrator must strictly review the source code on GitHub prior to execution, avoiding blind curl-to-bash piping. Utilizing the scripts' "Advanced Mode" is mandatory to ensure the LXCs are deployed on the correct internal VLANs (VLAN 30\) with static IP configurations, rather than defaulting to dynamic DHCP allocations.

To facilitate rapid, safe iteration outside the production environment, the developer requires a robust **Local Development Environment** that accurately mimics the complex Proxmox architecture. Using the developer's existing generic PC and the OpenWrt-capable WR840N router, the optimal approach involves installing Proxmox VE directly onto the generic PC. If the PC is currently running an OS that cannot be wiped, Proxmox can be virtualized via nested virtualization within VMware or VirtualBox. The physical WR840N router must be configured entirely in "bridge mode," operating merely as a dumb wireless access point connected to the PC's physical NIC. The virtualized Proxmox instance hosts VM1 (OpenWrt x86), which executes the actual DHCP distribution, VLAN tagging, and OpenNDS captive portal interception. This methodology guarantees that the firewall rules, routing behaviors, and API interactions tested locally translate seamlessly to the physical production deployment.

Regarding **Infrastructure as Code (IaC)**, attempting a full Terraform deployment introduces unnecessary complexity for a student-led project. However, infrastructure must be codified to ensure rapid recoverability. The recommended middle-ground involves utilizing Ansible. The community.general.proxmox Ansible collection possesses the capability to automate the instantiation of LXC containers, the configuration of network interfaces, and the provisioning of VM resources. Paired with standard docker-compose.yml configurations managed within Coolify for the application tier, this level of IaC provides the organization with a highly documented, version-controlled architecture that can be rebuilt reliably following catastrophic hardware failure.

## **Updated Architecture Decision Record**

1. **Architecture Segmentation:** The routing and captive portal infrastructure (VM1 \- OpenWrt x86) shall remain strictly isolated from the application orchestration layer (VM2 \- Ubuntu 22.04 \+ Coolify) across distinct virtual bridges to mitigate fatal iptables conflicts resulting from Traefik reverse proxy networking.  
2. **Credit Framework Compliance:** To strictly adhere to the BSP Circular 1166 exemption for closed-loop prepaid systems and avoid E-money issuer classification, the platform will technically prohibit peer-to-peer raw credit transfers, restricting inter-user transactions exclusively to "Session Gifting".2  
3. **Payment Gateway Isolation:** All third-party intranet applications hosted within the Coolify environment shall be restricted by egress firewall rules from interacting with external internet payment gateways (e.g., Xendit, PayMongo). All applications must interface solely with the local StudentHub Platform API utilizing the platform credit abstraction.  
4. **Hardware Scaling Preparations:** Connection pooling via PgBouncer and persistent append-only storage for Redis will be implemented during Phase 1 deployment to delay the exhaustion of the Intel N100's capabilities, explicitly addressing the limitations of the Linux conntrack table and allowing the hardware to scale up to 1,000 concurrent active users before physical migration.19  
5. **Telemetry and Notifications:** Outbound system notifications, including low balance alerts and account recovery OTPs, will bypass paid cloud infrastructure, utilizing the open-source Textbee API bridged via local Android hardware to permanently eliminate recurring operational expenditures associated with commercial SMS providers.8
